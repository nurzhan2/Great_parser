# banner_parser — парсер наружной рекламы из Яндекс.Панорам

> **Это форк.** Исходный парсер — [Hevilim/inmaps](https://github.com/Hevilim/inmaps),
> автор оригинального кода Hevilim1. Пайплайн (Яндекс.Панорамы → детекция →
> OCR → SQLite → Excel) написан не мной. Ниже — что в этом форке сделал я:
> диагностический слой, ревизия качества детекции и исправления по её итогам.
> Коммиты `af58482` и раньше — оригинальные; `4519bb9` и новее — мои.
>
> **Права на исходный код** (коммиты `af58482` и раньше) принадлежат автору
> оригинала — Hevilim1. Лицензия в оригинальном репозитории не указана,
> то есть условия использования, изменения и распространения этого кода
> автором явно не заданы. Форк опубликован как демонстрация выполненной
> работы по диагностике и ревизии; по вопросам прав на исходный пайплайн
> обращайтесь к автору оригинала.

## Что сделано в этом форке

**Диагностический слой** — новое:

- `banner_parser/runlog.py` — шапка запуска (каталог, интерпретатор, версии
  пакетов, свободное место) до тяжёлых импортов; перехват SIGTERM/INT/HUP/QUIT,
  `faulthandler`, `excepthook`; heartbeat с текущим этапом и RSS; ровно одна
  строка причины завершения. Логика чтения посмертного лога описана в модуле.
- `scripts/run_crawl.sh` — обёртка запуска: `cd` в каталог проекта,
  `python3 -u`, `YOLO_CONFIG_DIR`, предполётная проверка импорта, `flock`,
  проверка места по квоте, расшифровка кода возврата.
- `scripts/inspect_detections.py` — инструмент ревизии: показывает все детекции,
  включая отброшенные, прогоняет их через боевые фильтры и печатает, на каком
  шаге детекция умерла; размечает панораму боксами.

**Исправления по итогам ревизии** — в чужом коде:
промпты детектора, потолок «один баннер с панорамы», дедупликация,
разведение «это реклама» и «это недвижимость», `grid --road` на osmnx 2.x,
посев стартовой точки, запись кропов на диск. Подробности — в отчёте ниже.

# Технический отчёт: ревизия качества детекции

Замеры сделаны на живом сервере, на реальных панорамах Яндекса. Везде, где
приводится число, оно измерено, а не оценено; выборки маленькие и указаны явно.

## 1. Воронка: где терялись баннеры

Панорама `1298656268` (Марьино, строительное ограждение ЖК с рекламой),
кроп в максимальном зуме — то есть ровно то, что делает пайплайн:

```
182 детекции с порогом ≥0.10
 └─ 12 разобрано (все выше боевого порога 0.22)
     └─  8 прошли verify        4 отсеяны, из них 2 верно (дорожный знак, фонарь)
         └─ 3 прошли фильтр темы  5 убито темой «другое» из-за нечитаемого OCR
             └─ 1 СОХРАНЁН        ← return после первой удачной записи
```

Из 12 разобранных кандидатов в базу попадал один. Три причины, в порядке вклада:

1. **Тема определялась по тексту OCR.** OCR на реальных щитах даёт
   «Квартал Домаший», «samglftm», «Шшb CaMDIВП». Ни одно ключевое слово не
   совпадает → тема «другое» → `filter.only_category` выбрасывает баннер.
   Так терялось 5 кандидатов из 8.
2. **`process_panorama` возвращал первую сохранённую запись.** Ограждение с
   десятком рекламных секций давало одну строку за визит.
3. **Дедупликация.** Ключ округлял координаты до ~11 м и азимут до 10°, поэтому
   один щит с соседних панорам не склеивался: в базе лежало 4 записи на
   2 физических объекта.

## 2. Промпты OWLv2: точность 10% → 100%

Промпты содержали только рекламные классы, поэтому у модели не было варианта
«это не реклама»: рекламной меткой помечались дорожные знаки, фонари, детские
площадки и таблички с адресом дома.

Замер на одном наборе (3 панорамы, топ-12 детекций на каждую, порог 0.22
не менялся):

| | было: 5 рекламных промптов | стало: 3 рекламных + 7 отвлекающих |
|---|---|---|
| Панорама с рекламой: секции ограждения | 3 найдены | **те же 3**, score выше (0.55/0.53/0.52 против 0.53/0.51/0.49) |
| Она же: дорожный знак «пешеходный переход» | «a large advertising sign» 0.44 | «a road traffic sign» 0.567 |
| Она же: фонарный столб | «a large advertising sign» 0.385 | «a street lamp post» 0.400 |
| 2 дворовые панорамы, топ-12 каждая | 24 из 24 помечены рекламой | **0 из 24** |
| Точность по 36 детекциям | ~10% | **100%**, потерь среди настоящих щитов нет |

Отвлекающие классы уходят в модель вместе с рекламными, а детекции с
отвлекающей меткой отбрасываются. На магистрали это снимает медианно
**181 ложную детекцию с панорамы** (всего 5700 за тестовый обход из 31 панорамы).

Порог 0.22 не менялся: настоящие щиты идут с 0.49–0.55, вдвое выше порога,
и мусор отсекается меткой, а не порогом.

## 3. Найденные дефекты

| дефект | следствие | статус |
|---|---|---|
| Тема определяется по OCR-тексту, нечитаемый баннер → «другое» → выброшен | терялось 5 из 8 кандидатов | исправлено: «это реклама» и «это недвижимость» разведены, фильтр темы переехал в `export` |
| `return` после первого сохранённого баннера с панорамы | ограждение с 10 секциями → 1 запись | исправлено, потолок в конфиге |
| Дедуп не склеивает один щит с разных панорам (округление до ~11 м и 10°) | 4 записи на 2 объекта | исправлено: кластеризация по оценке положения щита |
| Дедуп склеивает разные щиты по одному телефону | федеральная кампания с единым номером схлопнула бы базу по стране | исправлено: телефон работает только вместе с географией |
| Кроп писался на диск до проверки дедупа | 24 файла при 5 записях, до 18 МБ мусора с панорамы | исправлено: файл пишется после принятия записи |
| `grid --road` падал с `TypeError` на osmnx 2.0.7 | команда не работала вообще | исправлено, добавлена совместимость с 1.x/2.x |
| `network_type="drive"` тянет внутридворовые проезды | обход жил по дворам, где наружной рекламы нет | исправлено: фильтр `motorway\|trunk\|primary\|secondary\|tertiary` |
| Стартовые координаты игнорировались при непустом состоянии | нельзя добавить второй старт в общую БД | исправлено |
| `df` на shared-хостинге показывает весь раздел | проверка места рапортовала 105 ГБ при квоте 12 ГБ | исправлено: учёт по квоте |
| Причина падения не читалась из лога | разбор занимал часы | исправлено: `runlog.py` |

Не исправлено (известные ограничения):

- **Геометрия боксов.** Боксы либо охватывают полсцены (щит занимает 10–15%
  кропа), либо вырождаются в полоску шириной 0.3% панорамы. Кропы пригодны для
  просмотра, но не как готовый ассет.
- **Нет минимального размера детекции.** Отсюда мусорные записи вроде кропа
  260×100 px с парковкой самокатов.
- **Дальность до щита не измеряется.** Дедуп исходит из допущения в 25 м; для
  щитов сильно ближе или дальше оценка положения смещается.
- **Качество OCR.** Телефон извлечён у 1 записи из 61; часть распознанного —
  мусор.

Один и тот же способ замера. «До» — обход по Марьино (дворы), «после» —

Рост числа записей — не только следствие правок: обход по магистрали идёт там,

Точность 64% считает наружной рекламой и вывески магазинов. Если считать только
классические конструкции (билборды, ситиформаты, брандмауэры, баннеры) — 25 из
61, то есть 41%. Остальное — заборы, обратные стороны щитов, дорожные знаки,
фрагменты столбов.

## 6. Второй этап: продукт, а не база координат

База наружки без телефона и темы никому не нужна. После первого этапа было
1 телефон на 61 запись (и тот мусорный) и 2 определённые темы из 61. Второй
этап целился в связку геометрия боксов → OCR → контакты.

### Отбраковка по размеру: размер НЕ разделяет рекламу и мусор

Гипотеза была, что мусорные кропы мельче. Замер на размеченной вручную выборке
(39 реклама / 22 мусор) её опроверг:

| | настоящие | мусор |
|---|---|---|
| медиана минимальной стороны | 143 px | **184 px** |
| медиана площади | 33 916 px² | 44 856 px² |

Ложные срабатывания в среднем КРУПНЕЕ: среди них заборы и стены во весь кадр.
Порога, разделяющего классы, не существует — при 80 px отсекается 6 мусорных
ценой 6 настоящих. Поэтому пороги поставлены как фильтр пригодности, а не
точности: `min_crop_area=5000` (нечитаемо) и `max_crop_area=800000` (забор,
а не щит). Отсекает 8 мусорных из 22 ценой 2 настоящих из 39.

### Геометрия: две гипотезы подтвердились, две нет

| гипотеза | вердикт |
|---|---|
| соседние детекции склеиваются в один огромный бокс | **нет**: `_dedup_overlaps` отбрасывает по IoU, а не объединяет |
| рассогласование координат обзорного зума и макс.зума | **нет**: пропорции W/H всех пяти уровней совпадают до 0,064% |
| текст режется по краям | **да**: `pad=0.0`, кроп ровно по боксу |
| бокс раздут проекцией | **да**: `_box_to_equirect` берёт min/max карты uv по прямоугольнику перспективного вида, а его прообраз в equirect — кривой четырёхугольник |

Исправлено отступом в 10% от размера бокса и обратным отображением вырезки в
перспективу (`rectify_region`). Обе правки в первой версии были сделаны с
ошибками, которые поймал боевой прогон: отступ задавался в долях панорамы
(3% от 17664 px = +530 px), а в выпрямлении был перепутан знак угла наклона —
кроп выходил чёрным.

### OCR: EasyOCR упирается в потолок

Замер на 25 кропах с эталоном, выписанным вручную; метрика — доля слов эталона
(≥3 символов), найденных в распознанном тексте:

| конфигурация | точность | время |
|---|---|---|
| **A базовый (как сейчас)** | **31,2%** | 48 с |
| B апскейл ×2 | 29,2% | 114 с |
| C апскейл + контраст + резкость | 28,3% | 37 с |
| D C + paragraph=False | 28,3% | 32 с |
| E D + мягкие пороги детекции текста | 30,1% | 30 с |

**Ни одна настройка не улучшила базовую.** Апскейл не добавляет информации,
контраст и пороги ничего не меняют. EasyOCR уверенно берёт крупный
рубленый шрифт («большой выбор», «качественные локальные бренды на
Wildberries») и разваливается на рукописных начертаниях и мелком тексте
(«Мам, домой не жди» → `J.. .wbufic .. ..n 609u.`).

Это потолок движка на данных такого качества, а не вопрос препроцессинга.

Точность выросла, контактов как не было, так и нет.

### Почему это тупик именно в OCR

На кропах финального прогона человек читает контакты мгновенно:

- `49` — баннер МВД: «8 (985) 277-78-79», «8 (926) 030-24-28»;
- `53` — билборд NOMAN: «+7 (495) 126-76-76»;
- `54` — билборд КИНОМАКС: «Подробности на kinomax.ru»;
- `33` — «www.indiaday.ru», `37` — «MPBS.RU», `9` — «spasstower.ru».

В базе по всем этим записям — пусто. Детекция нашла щит, геометрия дала
читаемый кроп, парсер контактов проверен на синтетике и работает. Не работает
одно звено: распознавание текста.

### Что делать дальше, с оценкой стоимости

| вариант | качество | стоимость на 100 000 кропов |
|---|---|---|
| EasyOCR (сейчас) | 31% слов | 0 ₽, ~1 с/кроп на CPU |
| PaddleOCR PP-OCRv4 | обычно лучше на сценовом тексте, нужен замер | 0 ₽, +200 МБ модель |
| Yandex Vision OCR | сильно лучше на щитах | ~20–50 тыс. ₽ |
| Google Cloud Vision | сильно лучше | ~$150 |
| VLM по кропу (Claude/GPT-4-class) | даёт текст, рекламодателя, тему и контакты одним вызовом | ~$300–1000 |

Инженерно правильный следующий шаг — VLM или облачный OCR: они закрывают
одновременно OCR, классификацию и извлечение рекламодателя, то есть ровно то,
ради чего база и собирается. Локальные движки в этой задаче упираются в
качество исходной съёмки.

## 7. Третий этап: замена OCR-движка

EasyOCR упёрся в 31,2% и ни одна из пяти его конфигураций не оказалась лучше
базовой — значит, вопрос в выборе движка. Кандидатов было три.

| движок | текст | рекламодатель | тема | с/кроп | статус |
|---|---|---|---|---|---|
| EasyOCR (контроль) | **31,2%** | — | — | 1,9 с | работает |
| PaddleOCR PP-OCRv5 ru | — | — | — | — | **не запустился** |
| VLM `claude-sonnet-4-6` | — | — | — | — | **не запущен: нет ключа** |

**PaddleOCR не удалось оценить ни в одной из двух доступных сред.** Локально
(Windows, Python 3.14) для `paddlepaddle` нет ни одного колеса: `Could not find
a version that satisfies the requirement paddlepaddle (from versions: none)`.
На сервере (Linux, Python 3.10) пара `paddlepaddle 3.3.1` + `paddleocr 3.7.0`
ставится, модели скачиваются, но `predict()` падает на каждом кропе:

```
NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute
not support [pir::ArrayAttribute<...>]
```

Ошибка не в классификаторе ориентации — она воспроизводится и с
`use_textline_orientation=False`, и с отключённым doc-unwarping, и с флагами
`FLAGS_enable_pir_api=0`, `FLAGS_enable_pir_in_executor=0`, `FLAGS_use_mkldnn=0`.
Это несовместимость PIR-формата моделей PP-OCRv5 со сборкой paddle под
процессор этого хоста. Ноль в таблице был бы враньём: движок не отработал
ни одного кропа, а не распознал плохо. Непроверенный путь — откат на пару
`paddlepaddle 2.6` + `paddleocr 2.9` со старым IR (ещё ~1 ГБ; свободно 4,4 ГБ).

**VLM не запущен: в окружении нет ключа API.** `ANTHROPIC_API_KEY` не задан,
`ant` CLI не установлен, активного профиля нет. Ключ — единственное, чего не
хватает: интеграция написана, проверена вхолостую и ждёт переменной окружения.

### Что сделано, несмотря на это

Движок вынесен за интерфейс и выбирается в `config.yaml` (`ocr.backend`:
`easyocr` | `paddle` | `vlm`) — сравнивать движки можно на живом обходе, не
трогая код. Проверено на сервере:

| требование | проверка |
|---|---|
| кэш по хэшу кропа | прогон 1 — 17 промахов; прогон 2 — **17 попаданий, 0 промахов** |
| отказ API не роняет обход | с `backend=vlm` без ключа: явная ошибка в лог, записи помечены «текст не распознан», обход продолжился |
| ключ только из окружения | `ANTHROPIC_API_KEY`; в `config.yaml` и в git его нет |
| ретраи с backoff | 4 попытки, пауза удваивается |
| тема и рекламодатель от движка | приоритетнее словаря; словарь остался запасным |

Готов и замер: `scripts/bench_ocr.py` гоняет любой набор движков по одним и тем
же кропам, считает долю распознанных слов эталона, а для VLM — точность по
рекламодателю и теме и **реальную стоимость по токенам из ответов API**.
Эталон расширен до 25 кропов с полями текста, рекламодателя (19 из 25) и
темы (25 из 25).

Запуск, когда появится ключ:

```bash

# Документация оригинального проекта

Собирает баннеры (билборды, сити-форматы, рекламные стенды) из Яндекс.Панорам в
таблицу Excel: **фото панорамы + вырезанный баннер + телефоны + тема + гео**.

> ⚠️ **Правовое.** Массовая выгрузка панорам нарушает пользовательское соглашение
> Яндекса (риск блокировок IP и юридических претензий). Параметры `min_delay` и
> `proxies` в `config.yaml` снижают нагрузку, но не отменяют риск. Ответственность
> за использование — на стороне пользователя.

## Пайплайн

```
meta-API (panoid, граф улиц, адреса)
   → сшивка обзорной панорамы (низкий зум)
   → детекция баннеров (репроекция в плоские виды + YOLO)
   → кроп bbox в МАКСИМАЛЬНОМ зуме (докачиваем только нужные тайлы)
   → OCR (easyocr) → телефоны (regex)
   → классификация темы (keyword / CLIP)
   → дедупликация (по телефонам / гео+азимут)
   → SQLite → выгрузка в Excel со встроенными фото
```

Ключевая экономия трафика: панорама целиком **не** хранится — детекция идёт по
обзору в низком зуме, а в макс.зуме докачивается только регион найденного баннера.

## Использование

```bash
# Одна точка (ручной регион баннера — режим демо/отладки):
python -m banner_parser demo --lon 37.748763 --lat 55.712394 --region 0.66 0.63 0.795 0.86

# Резюмируемый автономный обход Москвы (OWLv2 сам находит баннеры):
python -m banner_parser crawl --lon 37.7050 --lat 55.6480          # без лимита — крутить пока не исчерпается очередь
python -m banner_parser crawl --lon 37.7050 --lat 55.6480 --limit 200   # ограничить число панорам за запуск

# Длительный запуск — только через обёртку: она делает cd в каталог проекта,
# берёт python3, ставит YOLO_CONFIG_DIR, пишет лог с flush и держит блокировку.
scripts/run_crawl.sh --limit 500
tail -f logs/crawl_*.log          # смотреть прогресс
python3 -m banner_parser stats    # сколько баннеров найдено
# Остановить: Ctrl-C или kill -TERM <pid> — причина остановки попадёт в лог
# Продолжить: тот же запуск — состояние (посещённые+очередь) в БД, обход резюмируется

# Выгрузка в Excel (опц. фильтр по теме) и статистика:
python -m banner_parser export --category недвижимость
python -m banner_parser stats
```

## Запуск на shared-хостинге (Beget)

Хостинг **сносит всю пользовательскую сессию при выходе из SSH**. Проверено:
`nohup`, `setsid`, `screen` и `tmux` умирают через несколько секунд после
отключения — фоновый обход «на ночь» так не оставить. Вычислительно сервер
задачу тянет: одна панорама — ~30 с и ~2,5 ГБ RSS, лимитов по памяти и CPU нет.

Два рабочих варианта:

1. **Живая SSH-сессия** — `scripts/run_crawl.sh --limit 500`, терминал не закрывать.
2. **Планировщик в панели Beget** (crontab на хостинге нет) — команда:

   ```
   /home/s/<user>/<site>/inmaps/scripts/run_crawl.sh --limit 200
   ```

   Каждый запуск обрабатывает свою порцию и завершается сам; состояние обхода
   лежит в БД, поэтому следующий запуск продолжает с того же места. Блокировка
   в скрипте не даёт двум запускам пересечься, если предыдущий ещё не закончил.

### Как читать лог при падении

Лог пишется с flush на каждой строке, поэтому хвост переживает убийство процесса.
Первым делом ищите одну из строк:

| строка в логе | что произошло |
|---|---|
| `=== ЗАВЕРШЕНО` | отработал сам, в строке время и пик памяти |
| `=== СИГНАЛ` | остановлен извне (Ctrl-C, `kill`, обрыв SSH) |
| `=== ИСКЛЮЧЕНИЕ` | упал, трассировка следом |
| ничего из перечисленного | убит `SIGKILL` — OOM либо снос сессии хостингом |

В последнем случае смотрите последнюю строку `жив:` — она показывает этап и
занятую память на момент смерти. Строка `=== СТАРТ` в начале лога содержит
каталог, интерпретатор, версии пакетов и свободное место — то, чего не хватало,
когда обход падал с `No module named banner_parser`.

Зависший процесс можно опросить без отладчика: `kill -USR1 <pid>` выведет
в лог стеки всех потоков.
